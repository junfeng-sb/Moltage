# Configuration

## Current status

UI-R6 molecular preferences remain application-session state, except for approved Cube lighting/material values and the registered application-theme ID. Accepted orbital Ambient, Light intensity, Specular, Shininess, and the active theme ID are stored in `%APPDATA%\Moltage\view_preferences.json`. Lighting is restored for new Cube workspaces and the theme is applied before the main window is built after application restart; isovalue, colors, opacity, bond thickness, element colors/labels, and visual H filtering remain unpersisted. This narrow file is not project/profile configuration. Its schema 2 remains backward-compatible with schema-1 lighting files, which load with Future Light until a theme is explicitly selected. PM-R1 likewise introduces no generic GUI-preference store: a fresh Project Manager opens in Details view with Submission date newest first. Explicit Project Recycle Bin membership remains persisted because it must survive restart.

Transmission axis/grid/font/mirror, major/minor tick geometry and intervals, curve/legend, background/frame/margin, and output-canvas choices are tab-local presentation state and are not written to `view_preferences.json`, a project manifest, or a server profile. Current-view export stores only the user-selected local PNG/JPG/JPEG/PDF file; format and 1×–8× scale are not remembered and no export path is sent to a server.

Future Light is the compiled fallback selected when no per-user theme exists. The internal registry additionally contains Arctic Circuit, Pearl Quantum, Aurora Glass, Solar Paper, Event Horizon, and Ember Lab. Only those complete definitions are exposed by the upper-right Theme button. Each definition also owns high-saturation RGB colors for transient atom hover and the two density-fragment ring channels; these colors follow the active registered theme and are not persisted as independent user values. The chosen identifier is per-user presentation state in `view_preferences.json`; it adds no server-profile or project field and cannot affect scientific or remote behavior. A malformed or unregistered persisted ID fails explicitly rather than silently selecting a different saved choice.

No general application configuration framework is introduced. `server_profiles.json` is schema 12. It retains the optional AITRANSS runtime introduced in schema 4, structured runtime search and FHI-aims environment fields, scheduler identity, the complete optional LSF client-directory bundle, one optional canonical remote FHI-aims species-definitions root, scheduler-specific admission selectors, the two supported LSF resource policies, the explicit Slurm Step-4 AITRANSS launch policy, and one independent optional ORCA runtime plus unresolved discovery hint. Schema-1 through schema-11 profiles preserve their supported existing values, migrate with ORCA unresolved, and are rewritten only on the next save. Their admission selectors migrate to empty; legacy LSF profiles retain `SPAN_RUSAGE`; legacy Slurm profiles retain `SRUN` intent but reuse a path only when existing profile evidence provides an absolute `srun`, otherwise Step 4 remains explicitly incomplete until configured and verified. Legacy automatic LSF profiles may retain unresolved client directories until bounded preflight rediscovers them. Existing optional `email_notification_enabled` and `email_notification_recipient` fields remain backward-compatible. The authoritative project manifest is schema 10. Schemas 1–8 migrate to the unchanged `FHI_AIMS_AITRANSS` workflow, while schema-9 ORCA records retain their existing optimization/frequency evidence without inventing WBL results. New ORCA projects carry an explicit `ORCA` workflow identity, one required optimization stage, an explicit-user-action WBL stage with `RUNNING` / `SUCCEEDED` / `FAILED` state and hash-bound artifacts, and an optional frequency stage. The Project Manager always shows optimization and WBL as its two ORCA indicators; frequency is not a third indicator. WBL and frequency submission are available from `Calculation > ORCA` after geometry recovery. Existing FHI projects retain the two-side generator model, layer/spacing, ordered standard lattice identity, standard local-to-global mapping, apex, immutable reference corners, accepted roll, and signed same-layer extension identities and global mappings. Schema 7 migrates with empty extension collections; schemas 1–6 retain the existing bounded legacy migration, and no migration infers extensions from coordinates, suffixes, or atom counts. Historical Step-3/Step-4 attempt hashes remain unchanged. Complete schema 4–6 direct mappings use a bounded `LegacyAu59V1` decoder; normal legacy transport records without mappings are marked proof-required and mapping-dependent operations fail unless historical structure/contact evidence is unique. A recovered derived electrode mapping may retain an unknown roll as `null`; the application does not invent one. Local `known_projects.json` is schema 2: its existing `projects` cache is unchanged, and its separate `recycled_projects` array stores only project/profile UUIDs, remote path, display name, workflow identity, optional project submission time, and recycle time. Schema 1 loads with an empty recycle set and is rewritten only on the next local index mutation. This local schema change does not alter the remote project manifest. Legacy profiles load with notification disabled, no recipient, no species root, and no ORCA runtime. Existing input viewing, parsing, recovery, and byte-preserving retry remain available because historical `control.in` files embed their definitions. Every newly materialized Step-1, Step-2, Step-3, density, or standalone-export `control.in` requires the selected current profile's remote species root; restart-draft preparation may recover editable settings from the current attempt but materializes new bytes from that current server. Retry and restart-draft preparation retain the current profile's fixed environment/launch policy and never change the saved preset. Missing, mismatched, ambiguous, or unparseable attempt provenance fails explicitly; there is no hardcoded memory or saved-profile resource fallback. This feature adds no global restart setting. Step 4 uses a separate one-process resource model and does not rewrite the FHI-aims preset. New electrode geometry is generated by `MoltageAuPyramidV1`; it does not use packaged coordinate resources. `$nlayers` is independent from geometry: 4-layer/`2` and 5-layer/`3` are `AIMS_RECOMMENDED` from reviewed AITRANSS 051414 fcc(111) headers, 6-layer/`4` is `USER_SPECIFIED`, and 2, 3 and 7–10 require a manual positive value. Existing historical `tcontrol` values are preserved and never rewritten by this table. Layer tolerance is 0.03 Å, and leakage values come from validated current `s1i`/`s2i`/`s3i`, not new configuration. The self-energy format has no configurable switch: the external owner vocabulary is `empty`/`left`/`right`, while internal ownership remains `NONE`/`LEFT`/`RIGHT`. `config/server.example.yaml` remains an illustrative unread placeholder.

The UAC-elevated Windows installer contains no configuration snapshot. A fresh installation discovers no build-machine server profiles, projects, host keys, credentials, or logs. Its selectable application directory contains only installed program files; overwrite/upgrade installation keeps the stable application identity and does not read, replace, migrate, or delete existing `%APPDATA%\Moltage` files or Windows Credential Manager entries. The application, rather than Setup, performs one narrow compatibility import at startup: each recognized non-secret file from the former application-data directory is copied into `%APPDATA%\Moltage` only when the destination file is absent. Existing Moltage files are never replaced, and the former directory is neither changed nor removed. Uninstall removes application files and the installer-owned desktop shortcut only, while deliberately preserving per-user application state.

Application-owned density-task manifests and recovered payloads are stored under `%APPDATA%\Moltage\density_results`. This path is resolved from the safe per-user application-data base and never from the process current working directory; an unavailable safe base fails explicitly instead of falling back to a repository, installation directory, or filesystem root.

Status refresh has one 60-second overall UI-session deadline; it is not a saved server/profile/job parameter and does not change SSH authentication or calculation walltime. Stop/timeout restores controls without waiting for network I/O and retains last displayed task states. Closing the application detaches active refresh sessions; it never cancels their calculation jobs. Other remote operations keep their existing shutdown guard.

Cluster Execution Settings calls the application result stream **Output file name**. Slurm uses it directly for `--output`. LSF creates and redirects the job shell to it at execution start, while its separate scheduler report uses the deterministic derived name `<output file name>.lsf.log` through `-oo`. It accepts one safe filename relative to each job's explicitly fixed working directory and rejects directory or absolute-path input. Leaving it empty is allowed only as an intentionally incomplete saved profile after explicit confirmation. Any FHI-aims submission that consumes this preset value then fails locally and explicitly until a valid filename is configured, because its recovery and monitoring require a deterministic output name; task types that already own fixed attempt-specific output names remain unchanged. In Server Connections, the folder button beside **Remote project workspace** opens a read-only SFTP directory browser at the current workspace (or `/` when the field is blank), lists existing folders only, and applies only the selected directory to that profile.

Slurm profiles may store optional **Account**, **Partition**, and **QoS** values; LSF profiles may store optional **Queue** and **Project** values. Blank means use the scheduler/site default, and discovery never guesses these admission selectors. Only fields for the selected scheduler are retained or rendered. LSF additionally offers **Scheduler/site default**, which emits no `#BSUB -R` and leaves placement and memory reservation to the site, and **Structured span + rusage**, which emits the existing structured host/rank/memory requirement. No raw scheduler directive or resource-expression input is accepted.

An LSF preset has three additional scheduler inputs: **LSF configuration directory** (contains `lsf.conf`), **LSF library directory**, and **LSF server directory**. The scheduler command directory itself is `LSF_BINDIR`. Automatic detection retains matching `LSF_ENVDIR`/`LSF_CONFDIR`, `LSF_BINDIR`, `LSF_LIBDIR`, and `LSF_SERVERDIR` values advertised by the current or normal login environment, or tests only a bounded standard sibling layout derived from the verified command directory; it never scans the filesystem or searches for and directly sources a detected setup script. A bundle is accepted only when its files/directories are accessible, the required `bsub`/`bjobs`/`bhist`/`bkill`/`lsid` clients are executable, and the standard read-only `lsid` command initializes with that exact bundle. Manual LSF mode requires all three additional directories explicitly. Every used LSF client process receives the same four validated LSF directory variables. Slurm presets cannot store these LSF-only fields.

FHI-aims and AITRANSS versions, executable names, module names, and locations are per-server configuration and must never be hardcoded as deployment invariants. Runtime discovery recognizes supported executable-name families, while an existing profile may retain any previously verified explicit member. The explicit runtime path can also identify an installation through a supported `run_aims.mpi` wrapper layout; locating a binary or species root does not establish scientific/version compatibility between them.

## Manual runtime configuration and targeted discovery

Cluster Execution Settings exposes shared `General / Cluster` settings plus top-level `FHI-aims` and `ORCA` program pages. The FHI-aims page contains separate FHI-aims and AITRANSS subtabs. Its `Manual Configuration...` flow retains one installation directory **or** executable file per program, an absolute compatible FHI-aims `srun` or `mpirun`, one species-definitions root, and separate environments. The species-root field has its own read-only remote-directory chooser and never changes the project workspace. For Slurm Step 4, AITRANSS uses exactly one explicitly selected one-process mode: **Direct** invokes the configured executable itself, while **srun** requires a configured and remotely verified absolute executable path whose basename is `srun`. Finding a candidate may fill the path but never chooses the mode, and unavailable or unresolved `srun` fails before remote mutation rather than falling back to a PATH command. LSF does not show these Slurm-only AITRANSS launch controls.

The ORCA page has its own executable, environment, version evidence, validation status and actions. Its minimum optimization configuration is one canonical absolute POSIX path ending in `orca`, plus `None`, `Modules`, or explicitly trusted `Setup Script` environment preparation. No MPI launcher, basis path, frequency executable or separately configured WBL utility path is required. Manual validation is available for both Slurm and LSF and requires the selected environment to resolve `orca` to that same canonical executable. Automatic discovery is available only for Slurm and checks the login environment, the filled environment, and a bounded set of ORCA-named module candidates; it neither scans installation trees nor selects a newest version. Multiple candidates require an explicit choice. Version evidence outside 5.0.x, 6.0.x and 6.1.x blocks generation; unparseable version evidence permits only catalog choices maintained as version-common and remains visibly unverified. Starting WBL additionally requires an executable canonical `orca_2json` beside the exact ORCA driver recorded by optimization; it is verified at that action and is never resolved from a bare PATH command. A sibling `orca_2mkl` is optional and contributes only a Molden provenance artifact.

ORCA optimization settings are stored with the submitted stage rather than as server defaults. Method and basis start unselected. Charge starts at `0`, multiplicity at `1`, and Moltage checks only electron-count parity without guessing the scientifically correct state. Process count maps identically to scheduler task slots and `%pal nprocs`, with one CPU thread per task. `%MaxCore` is optional MB per process: a blank field emits no `%maxcore` and leaves ORCA's documented 4096 MB/process default behavior in force; a filled value is shown as `nprocs × MaxCore` planning information and is not presented as a hard memory bound. LSF `rusage[mem]` semantics remain site-defined and are not converted into an exact total-memory claim.

ORCA WBL settings belong to the completed project stage, not the server profile. The four linker choices (`SH`, `SMe`, `NH2`, and `Pyridine`) carry no numeric `Gamma_0` defaults. Both contacts require a positive eV value marked `HYPOTHESIS` or `CALIBRATED`; `Same as left` only mirrors the value entered by the user. Existing domain linker detection prefills the contact/linker pair only when exactly two supported, unambiguous candidates exist. A contact may also be selected from one-based atom labels in the recovered read-only viewer. Automatic projection is limited to reviewed def2 basis identities and shows the resolved valence model; parameter-evidence, projection, direction and manual-AO overrides are explicit Advanced settings. New dialogs read versioned UI starting values from `resources/orca/wbl_ui_defaults.toml`: generic Au `E_F = -5.1 eV` with vacuum zero is an editable `HYPOTHESIS`, not a universal facet or junction value, while the relative window `[-5, 5] eV` and `0.01 eV` interval are Moltage convenience defaults. Accepted values are persisted through the existing WBL settings model. These settings affect only the ORCA WBL hypothesis and do not alter scheduler resources, optimization input or the FHI/AITRANSS workflow.

Environment choices are Auto, No setup, Modules and Setup script. Only Modules shows module names, and only Setup script shows its path. Auto is an unresolved search request, never a runnable environment. No setup uses the server's login environment without module commands. Modules and setup-script configuration are independent for the two programs. Exact executable paths with an explicit environment can be applied without automatic discovery. An installation directory must first resolve to a selected executable. Apply edits only the outer working copy; outer Save persists it. Cancel does not save, and Enter does not close the manual dialog.

Discover Runtime and Find Missing use one shared search rather than a full module scan followed by a second fallback scan. Filled paths, launcher, species root, and explicit environments remain constraints; only complete candidates fill blanks, and multiple verified candidates require selection. A file whose environment or FHI-aims launcher is still unresolved is shown only as a partial candidate and is never converted into saved runnable configuration. Both programs are checked in configured/current login environments first. One cached PATH inventory per environment includes common cluster filenames such as `aims.cluster.scalapack.mpi.x`, `aims.step3.scalapack.mpi.x`, and `aitranss.synthetic.x`, plus all same-name MPI paths; realpath-equivalent launcher aliases are deduplicated without replacing their callable names. Launcher evidence is retained even when no FHI-aims executable is found, but it is reported only as an independent candidate because MPI/ABI compatibility cannot be inferred until the matching FHI-aims build is known. A known `run_aims.mpi` layout is read at most once (64 KiB) to derive the default binary. For each canonical FHI-aims executable, the search checks only bounded immediate installation layouts derived from that executable and accepts a species root only when its immediate `light`, `tight`, and `really_tight` children all exist; zero or multiple roots remain explicit manual-configuration outcomes. AITRANSS can be found as `aitranss*.x` in the immediate `bin`, `scripts`, or `libexec` siblings of a verified binary's real installation root, including when the PATH command was a user-local symlink. If a PATH command is a standalone copy, one additional bounded lookup uses each canonical PATH directory only as evidence: it checks immediate program-named children below that directory's installation root and the conventional `opt`, `apps`, and `software` containers. This is a shallow glob limited to `*aims*` layouts, not a recursive home or filesystem scan. A newly resolved FHI-aims environment can also guide the minimal AITRANSS support-module choice. Only when all directed checks find no binary does a nonrecursive, versioned-name lookup inspect up to 32 absolute PATH entries and then query an existing `plocate`/`locate` filename index once. Indexed hits are still required to be readable executable files with safe canonical paths and ELF calculation binaries. Existing binary candidates skip those path-only fallbacks. Only a directory explicitly supplied by the user receives the existing depth-3 bounded `find`; automatic discovery never substitutes a home-directory or whole-filesystem traversal when an index is absent. No wrapper, `salloc`, calculation binary or discovered setup script is executed.

PATH-derived command candidates are discovery evidence, not trusted final configuration. Their existing directories are physically normalized before a callable filename is retained; a remaining unsafe or non-canonical candidate is isolated and reported without aborting other bounded candidates. The executable, launcher and manually entered path selected for persistence still pass the strict canonical absolute-POSIX-path validator.

Only unresolved Auto environments enter module discovery. A known ELF binary is completed first from its observed direct-library and launcher gaps; broader program-name module alternatives are tried only afterwards. Support discovery reads one terse available-module catalog per environment and filters names anywhere in the full namespace, so a request for MKL also sees names such as `apps/mkl-*` on Tcl Modules sites whose `module avail mkl` prefix filter would not. Lmod `spider` remains a bounded fallback. Tcl display-only leading slashes are normalized at the listing boundary, while directory headings remain rejected. Support families are derived only from observed ELF names and handled separately, with direct-library families before a launcher-only MPI search. Candidates matching versions/families present in ELF RUNPATH/RPATH and resolved-library paths are tried first. An `mpirun` path is automatically accepted only when its installation prefix owns the MPI libraries actually selected for the executable; `srun` remains scheduler-owned and is not subjected to that ABI-tree comparison. Intermediate environments are ordered by known dependency metadata, remaining direct-library count, and launcher availability: resolving five MKL libraries while temporarily leaving one launcher gap is valid progress, so the next step can add the evidenced MPI module. FHI-aims resolves first; its established modules prioritize, but do not replace validation of, a minimal separate AITRANSS environment. Equivalent partial states for the same executable are collapsed. The former blind MPI-by-MKL Cartesian enumeration is not used. Verified alternatives within a successful program-module listing remain selectable; later tiers stop once both environments are found. Canonical module-backed results retain the accepted legacy srun settings path. Candidate count remains limited to 64; program-module environments are capped at 12, the filtered catalog at 256 lines with only the top 12 evidence-ranked support candidates probed, support probes at 20 per program, and improving chains at four modules and six distinct frontier states. Optional module exploration preserves a 16-command reserve inside the one overall 128-command / 120-second admission budget. A branch or listing-cap stop retains already found candidates and explicitly reports which branch stopped; a transport exception is never treated as a budget stop or absence. These are query-count bounds, not a promise that a running SSH operation is interrupted at the deadline.

Direct shared-library metadata is inspected with readelf and file/cache checks, never ldd or a calculation launch. Missing/unavailable dependency evidence remains visible and does not silently resolve Auto to No setup. These checks do not prove transitive dependency closure, MPI/ABI compatibility, compute-node availability, program startup or convergence. A different executable name carries an explicit unverified-workflow-compatibility note; locating it does not establish compatibility with inputs or outputs produced for another build. A user-selected setup script is executable configuration, not passive discovery data: Find Missing asks before sourcing it and never automatically sources a discovered script.

An incomplete result names the exact unresolved manual field and its likely target basenames or directory contract. FHI-aims reports Remote path, Environment, MPI launcher, and species-definitions root separately; AITRANSS reports Remote path and Environment separately. The status text directs the user to the corresponding Manual Configuration tab/field and lists representative `aims*.x`, `aitranss*.x`, `mpirun`, or `srun` names, or the required `light`/`tight`/`really_tight` children. If no filename index exists, it explicitly states that a runtime absent from PATH, module metadata, and evidence-derived sibling layouts needs one manually entered installation-directory hint. This is an intentional discovery boundary, not a silent fallback or proof that the software is absent.

Explicit runtimes use login-shell batch scripts consistent with lookup, selected environment setup and one foreground launcher. FHI-aims `srun` retains `--kill-on-bad-exit=1`; `mpirun -n <MPI tasks>` propagates the launcher's return status without guessed MPI-specific options, backgrounding, pipelines or a nested allocation. Slurm Step-4 AITRANSS renders either `exec <aitranss-executable>` or `exec <absolute-srun> --ntasks=1 <aitranss-executable>` from the explicit launch policy and never emits bare `srun`. The mpirun branch's failure/abort behavior requires separately authorized external-environment acceptance and remains unverified by offline tests. Only explicit runtime file/launcher availability and the calculation binary's ELF header are checked before submission; legacy submission scripts and the at-most-once/UNKNOWN policy remain unchanged. Slurm native mail remains `END,FAIL`. The species-definitions root is saved per profile and used only to read exact required files for new input materialization; it is never copied into a project manifest or treated as part of an existing self-contained `control.in`.

Orbital Cube selections and optional grid spacing are calculation settings, not server-profile or application configuration. Step 1 initializes the six frontier selections on; Step 3 initializes with no orbital states. Blank spacing emits no FHI-aims grid directive. An explicit Å spacing is converted deterministically to classic `cube origin`/`cube edge` records using the submitted structure and is recovered only through exact generated-input round trip.

The Step-1 orbital recovery and display configuration boundary is **fully accepted and frozen**. Available Cube filenames, their exact recovered-structure/project/profile binding, the currently displayed orbital field, and its button selection are transient workspace presentation state. The binding is created both by normal Step-1 recovery and by reopening Step-1 output geometry from its status indicator; it is not inferred from a later step. None of this state is written to the server profile, project manifest, calculation inputs, or installer. Each later orbital selection is fetched on demand from the bound managed project and held only in memory after its temporary download has been parsed. A validated contact-Au transformation may retain the binding through appended Au and explicit terminal-H removal, while arbitrary edits to the recovered atoms do not.

## Configuration, secrets, and scientific resources

### Configuration

Configuration selects environment-specific behavior and points to required resources. Commit examples containing placeholders only. A real local configuration must remain untracked.

### Credentials and secrets

Profile passwords are stored only through `keyring` using the native Windows Credential Manager backend, service `Moltage`, and UUID-derived key `server-profile:<UUID>`. A read first checks the Moltage service and then the former service identity so an upgraded installation can still connect; every new or changed password is written only under `Moltage`, and explicit deletion removes either identity. Clearing “Save password securely” and explicitly saving deletes that credential; deleting the profile also deletes it. The mail recipient is non-secret profile data. No SMTP username, password, app password, OAuth token, or SMTP transport is requested or stored. Passwords, private keys, and equivalent secrets must never be committed or written to profile JSON, manifests, indexes, recycle tombstones, logs, or status messages. SSH keys and other authentication methods are not implemented.

### Local lifecycle diagnostics

Submission milestones are written best-effort to `%APPDATA%\Moltage\submission_lifecycle.log`, rotated at 512 KiB with two backups. Records contain controlled event names plus bounded project, step, Job ID, and exception-type tokens where applicable. They never include passwords, credentials, input-file contents, SSH commands, remote paths/output, or exception messages. This log is non-authoritative, and logger setup or write failure is ignored so it cannot change submission or persistence semantics.

### Scientific resources and templates

The Phase 1C covalent radii are stored in `resources/chemistry/covalent_radii.toml` and are used for approximate molecular connectivity. The packaged H-Bi values are the Blue Obelisk Data Repository `radiusCovalent` values at pinned commit `abff999b6bc6a893252eed7df0fae52ddfeed9dd`, whose radius update identifies Pyykko and Atsumi, *Molecular Single-Bond Covalent Radii for Elements 1-118*, DOI `10.1002/chem.200800987`. They are single-bond additive radii `R(AB) = r(A) + r(B)`, already expressed in angstrom and redistributed from BODR under `CC0-1.0`. The resource metadata retains the exact source and license locators and notes BODR's legacy MIT metadata. Au-pyramid connectivity does not reinterpret the Pyykko Au radius as a bulk-metal bond rule: `MoltageAuPyramidV1` derives neighbors from integer lattice identity at `2.88372 Å`. That spacing is the rounded mean measured from the former Au56 standard cores and is a Moltage project geometry parameter, not a universal Au-Au equilibrium distance, experimental constant, or the former `2.89 Å` visualization cutoff.

Phase 1E-A-R2 steric screening instead uses `resources/chemistry/vdw_radii.toml`. Its H-Bi values, with Pm deliberately excluded to preserve the existing supported set, are the central free-atom equilibrium `R_free_vdW[alpha]` values from Charry Martinez and Tkatchenko, *Van der Waals Radii of Free and Bonded Atoms From Hydrogen (Z=1) to Oganesson (Z=118)*, ChemRxiv Version 2, DOI `10.26434/chemrxiv-2024-m3rtp-v2`, Electronic Supporting Information Table S1. Moltage converts those `CC-BY-4.0` values from bohr with the 2022 CODATA factor `0.529177210544 angstrom/bohr`, rounds to six decimal places, normalizes the Z=64 and Z=67 symbols by atomic number, and records these transformations in the resource. These are heuristic free-atom steric inputs, not universal bonded-atom contact distances. A structure requiring a Pm van der Waals radius fails explicitly rather than receiving an invented value.

`resources/anchors/au_placement_defaults.toml` owns the eight anchor-kind placement pairs plus the contextual paired-dicyano Cyano-N pair. The user-approved paired-dicyano values are C–Au `2.10 Å` / R–C–Au `111°` and Au–N `2.00 Å` / C–N–Au `121°`; ordinary Cyano-N remains `2.20 Å` / `179°`. Electrode coordinates are no longer packaged resources: `MoltageAuPyramidV1` generates deterministic 2–10 layer tetrahedral Au geometry and explicit lattice/reference identities at runtime, with six-layer Au56 as the default. Its backend and Geometry viewer may append same-layer Au sites from the same signed integer lattice at the unchanged `2.88372 Å` Moltage project spacing; extensions retain separate provenance and never alter the standard apex or three reference corners. Candidate cache, `AVAILABLE`/`BLOCKED` preview color, and current hover identity are transient per-workspace state rather than configuration or manifest data. FHI-aims species definitions are not application resources. New inputs read only the exact required definitions from the selected server profile's canonical remote root, with `tight` as the Step-3 default, and never infer, synthesize, or substitute another element or accuracy. Historical `control.in` files keep their embedded blocks and require no external species source for viewing, parsing, recovery, or exact-byte retry. Step-3 fixed directives are `output aitranss`, `KS_method serial`, and `restart aims.restart`; the application does not create or copy an `aims.restart` file. These resources have distinct meanings and must not substitute for one another.

The Au extension hover's predicted-bond endpoints, same-layer basis, dashed guides, and fading grid plane are transient derived presentation state. They add no user setting, profile field, manifest field, or scientific parameter.

## Failure policy

Missing required configuration, credentials, species defaults, anchor definitions, generated-electrode provenance, optimized structures, scheduler Job IDs, or AITRANSS prerequisites must produce an explicit failure. A malformed local recycle/index document also fails explicitly rather than silently re-showing suppressed projects. Permanent deletion requires explicit credentials/host trust plus exact selected profile, manifest identity/revision, direct-child path, and non-symlink-root validation. Do not silently substitute alternate values, files, algorithms, hosts, paths, or defaults.

Validation should distinguish malformed configuration from unavailable credentials, unreachable infrastructure, missing scientific resources, scheduler failure, technical program failure, and absent evidence of scientific convergence.

## Schema evolution

Introduce a concrete schema only alongside the first use case that consumes it. Keep the schema small, document required fields, and change it deliberately. Do not adopt a configuration framework, serialization system, backend registry, or migration layer during Phase 0.
