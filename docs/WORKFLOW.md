# Target Workflow

## Independent electron-density analysis

`Calculation → Electron Density Difference…` starts an independent one-job task
from the active applied geometry, without Step 1–4 prerequisites. See
[Electron Density Difference](ELECTRON_DENSITY_DIFFERENCE.md) for selection,
scientific definitions, single-job submission, three right-side component lamps,
exact shared-job cancellation, recovery and validation boundaries. Selection,
submission and status remain in the calculation tab; explicit successful result
recovery opens a separate read-only Density Difference view.

## Independent local tight-binding transmission

With any active Geometry tab containing at least two atoms and Connectivity,
`Calculation -> Local Tight-Binding Transmission...` opens a snapshot-backed,
session-local model. Linker recognition supplies contact candidates only; users
may instead pick or enter the two contact atoms. Every element onsite energy,
every unordered bonded element-pair coupling, both lead broadenings, numerical
eta, and the start-inclusive/end-exclusive energy grid must be explicit. Exact
atom and bond values override their batch values. Calculate evaluates the
orthogonal one-orbital, spinless, real symmetric, wide-band model locally and
opens the transmission curve in a separate result window; no chart occupies the
parameter workspace before that action. Atom energies and bond couplings appear
only for the current highlighted hover target. Later valid edits update the
existing result curve after a short debounce. Closing the tab
discards it. This path creates no project, file, server connection, Slurm job, or
AITRANSS result and cannot change Step 1–4 state.

## Current status

The stages below describe the implemented end-to-end workflow and its durable boundaries. Repository validation uses deterministic synthetic scheduler, program-output, junction, and transmission evidence; it does not claim acceptance on an external cluster.

The currently accepted implemented path is:

```text
Step 1 optimization
    -> Step 1 recovery
    -> Step 2 contact-Au optimization
    -> Step 2 recovery
    -> parameter-selected canonical Au pyramids (six-layer Au56 by default)
    -> Step 3 transport-convergence input
    -> Step-3 submission and recovery
    -> Step 4 AITRANSS submission and recovery
    -> validated non-spin TE.dat
    -> basic T(E) preview
```

No network connection opens at GUI launch and no timer or background monitor is added. Completion assessment runs only on explicit Refresh. Step 3 preserves scheduler, program, and scientific outcomes separately. Step 4 likewise preserves typed interface-overlap and self-energy file-format failures even when the scheduler reports `COMPLETED/0:0`. A successful non-spin result requires the authoritative current-attempt output, exact completion markers, parseable `tcontrol` result settings, a valid header, finite ordered points, and the complete requested energy grid. A post-run `tcontrol` byte-hash difference is diagnostic only, and earlier attempts and scientific inputs remain immutable. These boundaries are covered by synthetic offline fixtures rather than captured cluster jobs.

### ORCA optimization workflow (pre-acceptance)

ORCA is a separate workflow, not an additional FHI step. From an editable molecular structure, the user selects `ORCA`, a configured server profile, an explicit method and basis where required, charge, multiplicity, optimization/SCF controls, process resources, and optional `%MaxCore`. Moltage validates the reviewed version-capability catalog and charge/multiplicity parity, then previews deterministic `orca_opt.inp` and the exact scheduler script before any remote mutation. The script changes to the managed project directory and invokes only the verified absolute ORCA driver; `%pal nprocs` equals scheduler task slots, and no `srun`, `mpirun`, `which` or bare `orca` is used.

Explicit Refresh keeps scheduler outcome, ORCA normal termination, optimization convergence and final-geometry validation separate. A successful optimization requires all four evidence layers plus a hash-consistent submitted input and an ordered, finite `orca_opt.xyz`. The trajectory is optional. A non-empty `.gbw` is recorded as readiness evidence for the separately selected WBL stage; its absence does not negate optimization success. Before success, the accepted structure can already be reopened read-only from `orca_opt.inp`; after success, the verified `orca_opt.xyz` is used. These ORCA paths never read FHI-aims `control.in`, `geometry.in` or `geometry.in.next_step`.

After an ORCA structure is opened, `Calculation > ORCA` provides `Resubmit Optimization...`, `Calculate WBL Transmission...`, `Run Frequency...`, and `View WBL Transmission`; WBL/frequency are not Project Manager footer buttons. Resubmission preloads the persisted structured optimization settings into an editable dialog and creates a new managed project. Immediately before creation, Moltage reloads the source project and rechecks the exact prior Job ID: a confirmed queued/running Job is cancelled through the verified scheduler command first, a terminal Job needs no cancellation, and any unresolved status or cancellation outcome prevents the replacement submission.

`Calculate WBL Transmission...` is enabled only for a verified successful optimization whose `.gbw` hash is present. It is a user-confirmed post-processing action, not a scheduler job: Moltage first persists the WBL stage as `RUNNING`, verifies the `orca_2json` executable adjacent to the optimization's recorded ORCA driver, exports basis, MO coefficients and AO overlap from that unchanged `.gbw`, and performs the deterministic analysis locally. Preparing, running, success and failure messages are also shown in the originating ORCA Geometry workspace. A successful result changes the second ORCA status indicator to `SUCCEEDED`; a definite processing error records `FAILED` without changing optimization success. An optional sibling `orca_2mkl` may add a Molden provenance artifact but never substitutes for overlap evidence.

The settings dialog reuses the existing linker detector. Exactly two unambiguous supported contacts are prefilled in deterministic atom order, and choosing a different contact updates the detected linker. `Manual select in viewer...` temporarily hides the settings dialog and labels every atom one-based; clicking a supported S/N atom returns to the same settings without modifying geometry. The main form contains contacts, detected linkers, positive `Gamma_0` values and the energy window. `Same as left` mirrors the user-entered left coupling and is not a numeric Moltage coupling default. Parameter evidence, projection, optional direction and manual AO indices are descriptive Advanced controls; automatic projection identifies the actual derived valence model rather than only saying `AUTO`. New dialogs use the versioned editable Au `E_F = -5.1 eV` hypothesis, relative `[-5, 5] eV` window and `0.01 eV` sampling from `resources/orca/wbl_ui_defaults.toml`. The Au value uses vacuum zero and is a generic starting point, not a universal surface or junction Fermi level.

For reviewed def2 basis identities, automatic contact projectors use directional N valence `2s/2p` or S valence `3p`; S core `2p` is excluded. Unsupported/custom basis evidence, ambiguous geometry, missing overlap, or an unknown spin layout requires explicit manual evidence or fails without fallback. Symmetric Löwdin weights produce per-MO left/right broadenings. Restricted multiplicity-1 evidence evaluates every spatial MO once and persists only the spin-degenerate total in the conventional `G_0 = 2e^2/h` normalization; unrestricted open-shell evidence evaluates every Alpha and Beta MO and persists both curves plus their raw spin sum. The versioned CSV/JSON/SVG artifacts record this spin treatment and the corresponding total-only or per-spin summaries. A completed result opens in a dedicated current-view-export-compatible tab from `Calculation > ORCA` or by clicking the second ORCA status indicator. Its logarithmic axis uses typographic powers such as `10⁻³`, never E notation. Product text identifies this result as a linker-parameterized WBL `HYPOTHESIS`, not explicit Au-molecule-Au DFT-NEGF.

Project Manager always shows exactly two ORCA indicators—optimization and WBL—so optional frequency does not create a third lamp. Persisted WBL success is published to the project list before result presentation is assembled; a presentation failure reports an explicit display error without reverting the successful second indicator. FHI-only Step-3 resubmission, Step-4 self-energy retry, and the FHI transmission footer button are hidden for ORCA projects, while their existing FHI eligibility is unchanged. After verified optimization, `Calculation > ORCA > Run Frequency...` may separately create one `ORCA_FREQUENCY` stage. Its method, basis, dispersion, charge and multiplicity are inherited from the source optimization; the user chooses `FREQ` or `NUMFREQ` plus independent resources and optional `%MaxCore`. Recovery requires scheduler/program evidence, a `VIBRATIONAL FREQUENCIES` section, hash-consistent submitted input, and a dimensionally consistent `orca_freq.hess`. Classification follows ORCA's own imaginary-mode annotations without a Moltage numerical threshold and is worded as reported evidence, not proof of a global minimum. Frequency failure or uncertainty never rewrites optimization or WBL success and never starts WBL automatically.

The repository's automated ORCA and WBL validation is synthetic and offline. It opens no SSH connection and runs no licensed ORCA binary, so external installation compatibility remains separate acceptance evidence.

## Phase 2B1 persistent foundation

One `ServerProfile` owns its stable UUID, editable display name, host/port/username, Remote project workspace, save-password and auto-connect preferences, optional structured cluster execution preset, and optional Slurm-native email recipient. `Manage Servers...` answers how to reach the server; the separate `Cluster Execution Settings` task answers how future jobs should run; `Settings -> Email Notifications...` edits only terminal mail for the selected profile. Scheduler command location defaults to Automatic; a verified discovered bin directory may be cached, revalidated, and rediscovered if stale. LSF additionally stores safe absolute configuration, library, and server directories; the command directory supplies `LSF_BINDIR`. Automatic detection obtains a matching set from standard current/login-environment metadata or a small standard sibling layout derived from the verified command directory and confirms the complete set with read-only `lsid`; Manual LSF mode requires the user to enter all three additional directories explicitly. It does not locate or reuse a calculation/setup wrapper and introduces no filesystem scan. Runtime is entered in hours and normalized to integer minutes, memory is entered and stored as integer GB per node, and module names remain ordered. New presets enable no-requeue, no submission-environment export, inherited-Slurm-environment clearing, and module purge by default, with one OpenMP thread. Non-secret profile JSON, the application known-hosts file, and the local known-project index live under `%APPDATA%\Moltage\`. At first Moltage startup, each recognized non-secret file from the former application-data directory is copied only if its Moltage counterpart does not already exist. Passwords use Windows Credential Manager under service `Moltage` and key `server-profile:<UUID>`; reads fall back to the former service identity for existing installations, while all new writes use `Moltage`. They never enter profile/project JSON. Auto connect means resolve a saved password and open a short-lived verified connection when a remote operation requests it, not at startup and not as a permanent session.

Output file name is the application-output filename. Slurm maps it to `--output`; LSF redirects the job shell to it before environment setup so the file is created at job start and grows while the program runs. LSF reserves the derived `<output file name>.lsf.log` for its own `-oo` report and never overwrites the application output with that report. Both are safe filenames relative to the explicitly fixed job working directory, never remote paths. An empty value can be saved only after confirmation; an FHI-aims submission that consumes this preset value remains explicitly blocked until it is completed, while workflows with fixed attempt-specific output names remain unchanged. The folder button beside Remote project workspace in Server Connections opens an on-demand read-only SFTP browser and returns only an existing remote directory.

`Discover Runtime...` remains explicit and asynchronous. Normal detection and saved manual hints share one bounded search: configured environments and filled locations are checked first, followed by one cached PATH inventory (including common cluster/versioned basenames), immediate `bin`/`scripts`/`libexec` siblings inferred from a verified binary's real path, and a shallow program-name lookup below canonical PATH-advertised installation roots and their conventional `opt/apps/software` containers. That lookup expands only `*aims*` children and never recursively crawls a home directory or filesystem. A nonrecursive scan of at most 32 PATH directories and one optional existing `plocate`/`locate` filename index are used only while a program path remains absent; the index is read rather than rebuilt and every hit is independently validated. Only a directory explicitly entered by the user permits the existing depth-3 bounded search. Multiple MPI installations are distinguished from aliases, and a different AITRANSS versioned filename can be located beside FHI-aims without requiring a program module. A partial binary's actual ELF gaps drive bounded compiler/math/MPI completion before broader program-name module alternatives. Support discovery filters one namespaced module catalog, ranks candidates using observed ELF path/version evidence, and never assumes that `module avail <suffix>` searches namespaced modules. `mpirun` must belong to the resolved MPI-library installation tree before automatic selection. FHI-aims resolves first and supplies preference evidence for a separately validated minimal AITRANSS environment. Tcl listing-only leading slashes are normalized, and a transition that closes multiple library gaps while leaving one launcher gap remains eligible for the next evidence-led step. Equivalent partial states are collapsed, optional branches retain command reserve, and no blind MPI×MKL enumeration or second full module scan occurs. Canonical module-backed results retain the existing legacy settings and srun flags. `Manual Configuration...` still offers FHI-aims and AITRANSS tabs, one directory-or-file location per program, a FHI-aims MPI launcher, and conditional environment fields with English help. Find Missing honors filled constraints and asks about multiple complete candidates; partial candidates are displayed once per meaningful unresolved state and do not fill or overwrite fields. Its result lists each missing path/environment/launcher field, likely executable names, and where to enter the manual value. Finding only FHI-aims remains useful, including at a reported bounded-branch stop. No submission wrapper or scientific executable is run. Direct-library diagnostics and located filenames do not establish startup or scientific-version acceptance. A user-selected setup script requires explicit permission before Find Missing sources it; no discovered script is automatically sourced. Apply changes the working copy and outer Save persists it; cancellation never writes profile data. Transport exceptions remain connection errors, and no discovery occurs at application launch. Existing resources, scientific inputs, scheduler mail and submit-once/UNKNOWN handling remain unchanged.

The Slurm-native mail policy is fixed to `END,FAIL`. Enabled scripts contain exactly `#SBATCH --mail-user=<validated-recipient>` and `#SBATCH --mail-type=END,FAIL`; disabled scripts contain neither. The current profile value is applied when each Step 1, Step 2, initial Step 3, Step-3 retry, or Step 4 script is generated. Earlier scripts and attempts are never rewritten. Mail reports scheduler termination only; explicit Refresh remains authoritative for scheduler/scientific classification. Delivery continues after the application closes and uses no user SMTP credential or per-submission capability probe. Offline tests validate directive rendering, not external mail delivery.

Deferred notification work is limited to later explicit scope: `TIME_LIMIT_50/80/90` prewarnings, custom message bodies, direct Sendmail, `afterany` notifier jobs, SMTP, and periodic progress. None is part of the production MVP policy.

One `CalculationProject` is the entire four-step campaign: molecule optimization, molecule-plus-contact-Au optimization, transport convergence/preparation, and AITRANSS transmission. It is not a server profile, step, or scheduler job. The authoritative remote manifest for a new project is `<Project>/.moltage/project.json`; projects created with the former metadata-directory name remain readable and are updated in place. Presence of both names is an explicit ambiguity error. The local index records only `last_seen_revision` and identity/cache fields.

```text
ProjectName.YYYYMMDD/
├── .moltage/project.json
├── [Step 1 files]
└── molecule_Au/
    ├── [Step 2 files]
    └── transport/
        └── [Step 3 and Step 4 files]
```

The deterministic candidates are the unsuffixed dated name, then `_02`, `_03`, and so on. Initial directories are planned lazily. A structure with recognized linkers and no linker-attached Au recommends Step 1. Exactly two linker sites with two attached contact Au and no extra Au recommends Step 2 and marks Step 1 skipped. Attached contact Au plus additional Au is ambiguous. Every recommendation requires user confirmation and uses the accepted anchor detector output rather than a new geometry heuristic.

WF-R1 exposes that exact two-contact case contextually through the existing Step-2 action. Eligibility belongs only to the active editable local Geometry workspace and is independent of molecular file format; MOL bond order remains display-only. Missing, multiple, shared, ambiguous, or unrelated Au contacts, and already-complete electrode clusters, do not enter this path. Either the original imported structure must satisfy the rule or the current structure must be the matching result of accepted viewer placement; both together and sequential one-site applications are supported, while atom identity and bond topology must remain unchanged after the latest application. Viewer-added contacts are valid direct Step-2 input only; they are not relabeled as pre-optimized imported provenance and cannot enter direct Step 3.

## Stage A — Local molecular preparation

1. Import a molecular structure through `File -> New Geometry...` or drag one or more local files anywhere onto the main workspace. Both paths accept exactly the case-insensitive `.xyz`, `.mol`, `.in`, `.next_step`, `.cube`, and `.cub` suffixes and use the same loader. Multi-file drops open in source order; an already-open canonical path is focused without rereading or discarding its working edits. Mixed drops open supported files and report all rejected entries in one bounded warning; directories, non-local URLs, and unsupported suffixes never reach a parser. Normal four-column XYZ produces zero-based ordered atoms plus inferred connectivity, while MOL accepts only a single V2000 connection table with explicit type-1/2/3 bonds. A local FHI-aims `.in` or `.next_step` file containing direct element species needs no `control.in` and uses the same molecular-geometry parser as the server-backed project viewer. If adjacent `control.in` exists, its established mapping is used for aliases such as calculation-specific accuracy names; unresolved aliases fail instead of being guessed. A manually opened `.next_step` is read directly from its own complete molecular section without requiring the pre-run `.in`; server-backed optimized-structure recovery separately retains its submitted/optimized atom-count and ordered-element checks. Cube/CUB accepts one signed scalar grid, including an ORCA/Gaussian negative-`NATOMS` record with exactly one orbital identifier. ORCA coordinates are interpreted as Bohr; FHI-aims and unidentified producers request one workspace-local Bohr/Å confirmation, while scalar amplitudes remain unchanged. Cube opens as a read-only Geometry workspace and retains camera, reset, atom inspection, and measurement operations while disabling structure editing and workflow submission. True multi-dataset Cube remains unsupported. These paths never fall back to another parser. Each canonical resolved source path identifies one Geometry workspace. Different paths remain live in separate tabs even when basenames match, and switching tabs does not reread either source.
2. Infer approximate XYZ connectivity using `distance(i,j) <= factor * (covalent_radius(i) + covalent_radius(j))`. `Settings -> Bond Detection...` exposes the existing dimensionless factor in a positive `QDoubleSpinBox`, with the accepted `0.01`–`10.00` range, `1.10` default, two decimals, and `0.10` steps. Every value change immediately regenerates inferred-source workspace edges in place without changing their current atoms or coordinates. OK retains that graph/factor preview; Cancel restores the exact dialog-open factor and graphs. Explicit MOL graphs, display orders, and current working edits remain untouched. XYZ bonds render as single, while MOL type 1/2/3 bonds render as deterministic one/two/three parallel strands that share one logical edge. Connectivity itself still does not acquire bond-order or valence semantics.
3. Detect `NCS`, `NH2`, `Pyridine-N`, `SMe`, `SH`, `Alkynyl-C`, `Cyano-N`, and the conditional `Dicyano-C` site. Detection uses element identities and supplied connectivity only. A candidate dicyano center is C with exactly three non-Au neighbors, no H neighbor, and exactly two neighbors that satisfy the existing `C–N` cyano-arm topology; the third neighbor has no other element or topology requirement. Exactly two candidate groups in one structure activate both center-C sites. One group, or more than two, leaves every detected N as ordinary `Cyano-N` and adds no center site. When activated, all four original `Cyano-N` sites remain and no duplicate N anchor is created. Direct Au neighbors are excluded from structural matching and recorded separately. The validation viewer uses magenta shells for binding atoms and cyan shells for their attached Au.
4. Phase 1E-A-R2 computes anchor-specific proposals without preprocessing the stored structure. Existing anchor kinds retain their accepted behavior. Dicyano-C uses C–Au `2.10 Å` and third-neighbor–C–Au `111°`, choosing the hard-sterically-valid cone direction that makes its two Au–C–N angles as equal as possible. The four Cyano-N sites of an activated pair use Au–N `2.00 Å` and C–N–Au `121°`, selecting the direction farthest out of the local two-CN-arm plane. A simultaneous pair of special sites must occupy opposite aligned local-plane sides and then follows deterministic clearance/separation ordering. A single/degraded ordinary Cyano-N retains its existing `2.20 Å` / `179°` defaults. No new hydrogen-removal rule is introduced.
5. The desktop viewer exposes a left-side Electrode Builder. Selecting any unoccupied supported kind immediately produces the accepted semi-transparent preview. Done consumes the currently displayed proposal objects without invoking placement again, applies them atomically to the working structure, removes scheduled H atoms, clears virtual annotations, redetects anchors, and renders appended Au as opaque base atoms with attached-Au shells. An authoritative old-to-new mapping preserves imported orders on surviving molecular edges; every new contact-Au or generated-electrode edge is visual single. Applied sites become disabled. `Save geometry.in` is enabled only after application and delegates to the existing writer. Each Geometry workspace owns its builder content and proposal state; the single dock shell displays only the active Geometry's content and is unavailable on Transmission tabs. The dock's canonical toggle action is the icon-only `Show/Hide Electrode Builder` toolbar command; the underlying implementation remains Au-specific.

For manual inspection, activate the ruler and pick any two distinct atoms to display their explicit Cartesian distance in Å, or activate the angle tool and pick A, B, C to display the A-B-C angle with B as the vertex. Each toggle remains active for repeated measurements. Incomplete picks use a dedicated translucent amber shell in the existing batched highlight actor plus temporary 1/2/3 order labels; Escape clears only that feedback. A distance value follows the projected guide direction with a camera-aware perpendicular display offset. Every completed angle explicitly renders dashed A-B and B-C measurement guides, even without chemical bonds. Completed graphics and creation-ordered rows remain until Clear removes all current-tab measurements and incomplete picks, right-click `Delete measurement` removes one complete stable-ID overlay, or a newly loaded structure clears the whole session. The panel opens only with the first completed result (second distance atom or third angle atom), never on tool activation. Clear retains the active measurement tool. Replacing an atom preserves completed measurements; deleting an atom removes only measurements that reference it and remaps every surviving atom index. Measurements never add bonds, change coordinates, affect Au placement or Step-3 eligibility, or enter saved/generated/project files.
